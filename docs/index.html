cobarith

Where Python translations of real COBOL arithmetic store a different value than the COBOL program does. Every supported arithmetic statement in AWS CardDemo runs through GnuCOBOL and through four Python translations, and the stored values are compared case by case.

One real example

The next transaction ID can repeat the last one

CardDemo's bill-payment program COBIL00C, line 217, makes the next transaction ID:

       05 WS-TRAN-ID-NUM   PIC 9(16) VALUE ZEROS.
       ...
           MOVE TRAN-ID     TO WS-TRAN-ID-NUM
           ADD 1 TO WS-TRAN-ID-NUM

A double cannot hold every integer above 253, and a 16-digit ID goes past that.

Last ID9625004552692988
GnuCOBOL stores9625004552692989
Python float stores9625004552692988 same as the last ID

Both float translations store a wrong ID on 33 of 1,000 random inputs for this statement, sometimes repeating the last ID and sometimes skipping ahead.

At the top of the field the storage rule shows instead. 9999999999999999 + 1 leaves 0 in a PIC 9(16) field in COBOL, while a translation without that rule keeps 10000000000000000.

The inputs span each field's whole picture range, so this shows exposure. It is not a claim that CardDemo's real IDs get that large. Both values come from results/statements.jsonl (COBIL00C:217:ADD).

Why it matters for a migration

The risky part is the step that stores the result

  • COBOL keeps fixed-point decimals exactly and truncates toward zero when it stores a result. Python float and round() do neither reliably.
  • ROUNDED in COBOL sends halves away from zero. Decimal with ROUND_HALF_EVEN sends them to even.
  • A result too large for its field is cut to its low-order digits (or, with ON SIZE ERROR, left as it was), not raised as an error.
  • COMP fields are binary, and the compiler's truncation setting decides whether an overflowing value wraps.

So a translation can look right in review and still store different money and IDs. Checking each statement against the compiler finds those cases directly.

The four translations are written for this measurement and stand for hand or tool translations in general. Nothing here is a claim about any vendor's translator.

Limits

What this does not show

  • It is a measurement on CardDemo. It is not a compiler, a translator or a claim of general COBOL compatibility.
  • The reference is GnuCOBOL 3.2 with -std=ibm only. Whether IBM Enterprise COBOL agrees depends on its TRUNC option, which is not tested.
  • Statements are measured one at a time, with no data flow between them.
  • The final automated code review found four medium issues. None touches a statement CardDemo contains, and none is fixed. They are listed under Technical details.

Technical details

Method, results and gaps

How it works

  1. source.py reads fixed-format source (columns 8 to 72, comments and continuation lines) and expands COPY and EXEC SQL INCLUDE.
  2. data.py parses PICTURE clauses into digits, scale, sign and capacity, and resolves qualified names.
  3. stmt.py parses each ADD, SUBTRACT, MULTIPLY, DIVIDE and COMPUTE into exact assignments, or marks it unsupported with one reason.
  4. cases.py makes pinned random inputs and z3-solved boundary inputs: a rounding tie, an exactly representable value, an overflow, a negative value for an unsigned field.
  5. harness.py generates one GnuCOBOL program per statement, runs it on the cases and prints every receiving field, so the stored value is measured.
  6. translate.py computes the same statement five ways (below).
  7. experiment.py writes results/metrics.json and one record per statement in results/statements.jsonl.

Known gaps

The last automated code review found four medium issues. None touches a statement CardDemo contains, so the measured results stand, but they are real and not fixed.

  • A sign and its digits split across a continuation line are refused as unsupported. CardDemo's 11 continuation lines are all inside HTML string literals.
  • COPY REPLACING of a word also rewrites the same text inside a quoted literal. CardDemo's only copybook copied with REPLACING (CSSETATY) has one literal, '*'.
  • There is no compiler-backed unit test for 32-bit COMP wrapping (16 and 64 bits have one).
  • The harness's compile-failure and wrong-output-count paths have no tests. Either failure stops the experiment, and neither can change a stored value.

Reproduce

Python 3.12 or later and GnuCOBOL 3.2 (brew install gnucobol on macOS). The run takes about 25 seconds and reproduces both results files byte for byte.

python3 -m venv .venv && . .venv/bin/activate
pip install z3-solver==5.3.3.0 ruff
make test        # 115 tests
make lint
python experiment.py --out results/metrics.json
python demo.py --readme README.md --out README.md

CI runs lint, the data check and the tests on Ubuntu with GnuCOBOL 3.2.
